# 工作流与人工 Gate

## 用户步骤

### 首次使用：6 步

1. 一并提供已有简历、JD 或投递链接、公司、岗位和模板。
2. Agent 提取岗位最看重的能力与关键词，并初步检查简历匹配和风险。
3. Agent 只针对影响匹配结论的内容提出 3-6 个问题，用户补齐事实。
4. 查看匹配诊断与定制策略。
5. 查看改写和 30 秒 HR 红队复核，逐条接受、修改或驳回。
6. 确认后获得 HTML、PDF 和修改记录。

### 后续复投：5 步

事实库已存在时跳过第 2 步。不要重新询问已确认事实；只在 JD 让旧事实失效、出现冲突或确有岗位关键缺口时补问。

用户的简历和 JD 应尽量同时提供。先读取 JD 再补问，能够避免收集与目标岗位无关的信息。

如果用户只提供投递链接，先使用 `prepare --jd <url>` 读取页面。公司和岗位名称允许自动识别，但必须在事实确认前核对；链接无法读取时回退到粘贴 JD 或文件。

## 内部执行顺序

1. 解析输入并检查文件可用性。
2. 归一化事实，区分 `verified`、`unverified`、`conflicting`。
3. 提取 JD 要求，标记 `must` 或 `preferred`，提炼最看重的 5 项能力和关键词。
4. 以 JD 为靶心，逐条检查简历：哪些经历最匹配、哪些是废话、为什么 HR 可能跳过，并关联证据标记 `strong`、`transferable` 或 `gap`。
5. 只补问能改变匹配结论或改写边界的问题。
6. 按“匹配度 × 证据强度 × 可读性 ÷ 决策成本”生成定制策略和篇幅预算。
7. 按“要求 -> 证据 -> 改写”生成逐条差异，每段采用“做了什么 -> 怎么做 -> 结果怎么样”。
8. 以 HR 视角做 30 秒红队复核，修复表达问题，再校验并导出交付物。

## Gate 1：补齐事实

进入条件：简历文本和事实库已初步解析。

输出格式：

```text
已确认事实摘要：
- ...

需要确认（最多 6 问）：
1. ...
```

完成条件：

- 答案已回填到 run 内的 `analysis/profile.json` 和 `analysis/evidence.json`。
- 影响岗位匹配的冲突已解决。
- 用户明确确认事实边界。
- `job.json.confirmations.facts_confirmed = true`。
- `resume_agent.py promote --run <run-dir>` 已将确认结果同步回长期事实库。

失败处理：任何时候出现新事实，都先补充证据 ID，再进入改写。

## Gate 2：红队复核与确认改写

先模拟招聘方：

```text
假设你是该岗位 HR，只看这份简历 30 秒，你会不会让候选人进入面试？
如果不会，最可能卡在哪？
```

输出最多三个最关键阻塞点。表达、排序和关键词问题必须先修复；真实证据缺口保留为 `gap`，不能通过扩写、拔高角色或补造数字解决。

每条 `ResumeRewrite` 用一行展示：

```text
[rw-001] 原文：...
        新描述：...
        依据：evidence-001
        理由：强化 JD 对流程闭环的要求
        风险：无
```

完成条件：

- 每条改写状态为 `approved` 或 `rejected`。
- 没有 `proposed`。
- `requirements.json.thirty_second_review` 已记录复核结论、阻塞点和改进动作。
- 完成“10 秒测试”：仅看目标岗位和经历开头，能说出最强三条匹配证据。
- 用户明确确认最终文本。
- `job.json.confirmations.rewrites_confirmed = true`。

未确认改写时不得运行 `finalize`。

## 事实冲突与缺口

冲突示例：

- 简历写“负责”，原始事实只能证明“参与”。
- 两个文档对同一结果给出不同数字。
- 时间范围与公司经历时间不一致。
- JD 要求某项技能，但事实库无对应证据。

处理原则：

- 冲突未解决前停止。
- 无证据的岗位要求只能显示为缺口，不能补写到简历。
- 可以重排、压缩、换词和突出已有事实，不能改变事实本身。

## 版本与恢复

- 每次投递创建独立 run，不覆盖旧版本。
- run 内保存输入、事实快照、需求、改写、校验结果和交付物。
- 用户要求重做时，复制当前 run 的 JSON，创建新 run；不要直接在已交付目录上覆盖。
- 事实库更新只写 `store/profile.json` 和 `store/evidence.json`，同时保留修改来源。
- 事实确认后使用 `promote` 更新长期事实库；不要直接覆盖其他 run 或已交付版本。
